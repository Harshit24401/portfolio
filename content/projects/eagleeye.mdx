## Problem / context

Every production deployment at Optum goes through a change request: a form describing what's changing, why, how it was tested and how to roll it back. Reviewers had to check by hand that the form, the user story, the technical spec, the test evidence and the code all told the same story. They often didn't. Gaps showed up late, in review or after release, and each one cost engineer time. The cost was highest during release windows, when volumes spike.

I built EagleEye during Optum's 10-week Technology Development Program internship: an agentic review layer that checks a change request before a human reviewer ever opens it.

## What I built

A developer submits the change request through EagleEye's form. EagleEye gathers everything related to that change from the systems where it really lives, instead of trusting what was typed: the user story in Rally, the technical spec, the test evidence, and the GitHub repository and branches. It then runs a group of specialised agents over that context. Each agent checks one thing and returns a score, its reasons and recommendations:

- **Change intelligence:** do the form and the user story agree, and is anything missing or contradictory?
- **Incident intelligence:** have changes like this one caused incidents before?
- **Tech spec:** does the technical specification actually cover what the requirement asks for? This uses retrieval over the document, with evidence quoted from it.
- **Performance validation:** is there enough performance testing for the expected production load?
- **Security onboarding:** is the repository really onboarded to the required security tooling, and if not, is the exception justified?
- **Job validation:** is every batch job in the change registered and monitored before it goes live?
- **Deployment risk:** do the earlier signals add up to an acceptable risk?
- **Deployment rollback:** find the last known-good container image from CI history, so a rollback is one step instead of an investigation.

A summary step combines the agents' results into a weighted quality score, a risk level, prioritised recommendations and an AI code review of the diff. The developer and the production team get it by email.

**Orchestration.** The agents are nodes in a LangGraph graph, so groups of independent checks run together, and a failure in one agent is contained instead of breaking the run.

**Grounded, not guessed.** The checks read from the source systems, not only from what the developer typed. The tech-spec agent embeds the document, retrieves the passages relevant to each requirement, and quotes them as evidence. A finding says exactly where the spec does or doesn't cover something.

**Explainable by design.** Every score comes with its reasons, so a reviewer can see why a change passed or what to fix, not just a number. Critical gaps are highlighted before the change reaches production review.

**Stack.** Python, Flask and LangGraph. Azure OpenAI for reasoning and `text-embedding-3-small` for embeddings, with Qdrant as the vector store. Oracle for data. RAGAS to evaluate the retrieval. Deployed with Docker and Helm on Kubernetes.

## Results or aim

- In production by week 8 of the internship, supporting the Production Services team's deployment reviews, and refined from their feedback.
- Aimed at catching about 60 post-deployment defects a year, roughly 120 engineer-hours.
- Reviews start with complete, consistent information, and the same validation standard applies whoever the reviewer is.
- 1st place in India and Ireland, and 2nd globally, at Optum's Technology Development Program intern Shark Tank.
